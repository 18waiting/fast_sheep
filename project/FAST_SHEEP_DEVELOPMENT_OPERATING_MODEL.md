## 1. 产品方向（范围约束）

快羊是**安静运行、AI 优先、必要时人工接管**的拼多多多店铺客服客户端。

核心使用闭环：

1. 打开客户端，登录并管理多个拼多多店铺。
2. 系统在后台接收消息。
3. AI 用正确的店铺上下文与知识生成回复，在允许范围内自动处理。
4. 正常处理时前端保持安静，只显示轻量状态；用户点开才看详情。
5. AI 无法处理、缺依据或失败时，明确提醒人工接手。
6. 人工能看到上下文、完成回复，并确认待办已处理。

**原始拼多多客服工作台不作为快羊的主要使用界面。** 若接入方式需要保留它，只放在登录、排障或兜底入口，而不是让商家日常围着它操作。

范围判据（单一问题）：

> 它是否直接帮助完成「登录店铺 → 收到消息 → AI 回复 → 必要时人工接管」？

如果不能，就不作为当前阶段优先事项。

## 2. 三个使用区域

功能分组建议，不要求推翻现有界面重做。

| 使用区域 | 用户要完成的事 | 设计重点 |
| --- | --- | --- |
| 店铺管理 | 登录、查看连接状态、开启或暂停 AI | 区分「店铺已连接」与「AI 已启用」，避免误判 |
| 运行概览 | 了解是否正常运行、是否有待处理问题 | 正常时安静，异常时明确，不逐条弹窗打扰 |
| 会话详情与人工待办 | 查看上下文、转人工原因、人工回复 | 提示可直接进入对应店铺与会话，操作后有明确结果 |

**提示策略：**

- 正常 AI 回复：轻量计数、状态或活动记录。
- 需要人工：可见、可点击、不易丢失的待办。
- 连接失效或持续失败：明确显示系统无法正常服务。

> 「前端安静」不等于「故障静默」。

## 3. 暂缓项（除非成为闭环明确阻碍）

- 把原始客服工作台完整搬到快羊前台。
- 通用多平台框架与与当前需求无关的扩展能力。
- 复杂多 Agent 编排。
- 大而全的统计报表、管理后台、装饰性页面。
- 自动退款、改价等超出客服消息回复的业务动作。
- 为架构整齐而做的大范围重写。

已有模块如果不妨碍交付，不必专门拆掉。**先停止扩张，比立刻清理历史代码更重要。**

## 4. 按可验收闭环推进（六步验证顺序）

不以「先做完所有底层 → 再做 AI → 最后做前端」为主要推进方式。每轮交付一段能实际演示的完整行为。

> 这是**验证顺序，不是重做要求**。已完成且有验证依据的部分直接复用。

1. **一条消息能正确进入系统** —— 消息归属店铺/会话明确；详情可见；重复到达不产生重复处理任务。
2. **能生成有依据的回复草稿** —— 用正确店铺的上下文与知识；依据不足不编造；可验证生成结果，此阶段不要求自动发送。
3. **完成一次受控发送** —— 在明确授权测试范围内由人工确认发送；对象与草稿所属店铺/会话一致；区分成功、失败、结果未知。
4. **AI 无法处理时人工真的能接住** —— 失败产生人工待办而不只是写日志；提示能打开正确会话并显示原因；接管后该会话未发出的 AI 回复被拦截；处理完待办状态正确更新。
5. **接入第二家店铺，验证隔离** —— 身份、知识、待办、发送目标不混用；一店暂停 AI 不影响另一店；单店连接异常可识别提示。
6. **开放有限范围自动回复** —— 只对已验证、范围明确的场景开放，其余进入人工待办。不以模型自报「有信心」作为自动发送条件。

> 人工确认是验证阶段的过渡措施，**不是把最终产品改成逐条审核工具**。最终目标仍是 AI 自动处理为主。

## 5. 最低保障（保留，不因提速而省略）

产品层面做减法，实现层面保留底线：**不串店、不重复回复、不在人工接管后抢答、不把未知结果当成功。**

| 关键问题 | 应验证的结果 |
| --- | --- |
| 店铺隔离 | A 店消息不会使用 B 店知识，也不会发往 B 店会话 |
| 重复处理 | 同一消息重复到达不产生重复回复 |
| 人工接管 | 接管后尚未发送的 AI 回复被拦截 |
| AI 无法完成 | 缺依据、超时或出错时进入人工待办 |
| 发送不确定 | 结果未知时不盲目重发，先核实或交人工 |
| 敏感信息 | 凭证与客户敏感内容不必要地暴露在日志或界面 |

验证分层：开发时用模拟消息/固定样例/可控失败快速回归；跨模块行为跑完整链路；真实平台交互在明确授权后受控验证。

> 模拟测试通过 ≠ 真实接入可用；真实接入出问题 ≠ 每次都要重审全项目。先按失败证据缩小范围。

## 6. 工作方式（本次流程简化的核心）

默认开发流程收敛为：

> 明确一个可验收结果 → 必要的局部调查 → 连续实现与测试 → 修复发现的问题 → 交付验证结果。

定位问题、阅读相关代码、调试、补测试、修复普通失败，原则上属于**同一个任务**，不因每次普通失败就要求 Owner 重新批准。

### 按风险决定检查深度

| 工作类型 | 建议方式 |
| --- | --- |
| 小范围界面调整、已知缺陷修复 | 直接实现，执行相关检查，交付结果 |
| 跨模块但目标明确的功能 | 先给简短计划，再连续实现、测试、修复 |
| 店铺身份、凭证、发送机制、数据迁移变更 | 先做针对性设计检查，明确影响与验证方法 |
| 真实账号操作、真实消息发送、生产发布 | 取得明确授权，并限定操作范围 |

### 两种权限必须分开

- **开发自主权**：在批准范围内自行读代码、修改、运行测试、修复问题。
- **实际业务操作权**：登录或操作真实账号、向真实客户发送消息、修改生产数据、发布上线。

**扩大前者不等于自动授予后者。**

### 只在以下情况中断

1. 必须改变已确认的产品行为或验收目标。
2. 必须扩大权限，或改变身份、安全、真实发送边界。
3. 涉及破坏性数据变更或不可逆操作。
4. 缺少凭证、环境或关键产品决策，确实无法继续。

普通测试失败、实现细节调整、已知范围内的缺陷，不自动升级为新的审计任务。

### 与既有治理结构的相容性

- DEC-022 的 `Phase → Milestone → SHEEP Task → Acceptance Gate` 结构保留。
- Codex 结果集合 `COMPLETE / PARTIAL / FAIL / NOT_RUN` 与 Controller 复核 `PASS / REPAIR` 保留。
- Controller 复核仍是任务边界上的正式闸门；本模型不取消它。
- 本模型改变的是**同一批准范围内的工作方式**：不再为每次普通失败或同一问题的重复担忧开启新的审计循环。
- 对每次都会担心的同一个问题，优先建立**可重复运行的回归检查**，而不是反复写文字分析。

## 7. 任务表达模板

每个任务只明确四件事：**目标、范围、验收、停止条件。**

```text
任务：<补齐某段可验收的完整行为>
如现有实现已满足其中某项，验证后复用，不重复建设。

目标：
<用户完成后能做什么>

范围：
复用现有架构，不增加新框架，不进行无关重构。
不改变真实发送权限，不执行未经授权的真实账号操作。

验收：
1. <行为/测试判据>
2. ...

执行方式：
在本任务内完成必要调查、实现、测试和修复。
普通测试失败请自行定位并继续修复，不要反复停下来申请审计。
环境阻塞时说明已完成部分、阻塞证据与需要 Owner 提供的内容。

仅在改变产品目标、扩大权限、破坏性数据变更，
或需要真实账号操作时，停下来询问 Owner。

交付：
新增能力、修改内容、执行过的验证、未验证或未解决的问题。
不要把未验证写成已完成。
```
